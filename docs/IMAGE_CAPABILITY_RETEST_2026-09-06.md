## 测试方法

直接使用本机当前图片接口配置调用 `/v1/images/generations`，模型沿用项目配置（默认 `gpt-image-2`）。每次生成一张红色陶瓷茶壶，读取上游原始图片文件的真实像素，不经过页面固定质量逻辑，也不启用本地尺寸规整。接口密钥、上游地址、图片地址和原图不提交 Git。

分三组：相同提示词只改变 size/quality；使用线上 `buildXiGeneratePrompt` 将尺寸写入提示词；进一步在提示词中明确要求 high 质量及原生 2048 像素。

本测试只能说明当前接口、模型路由和这些样本的行为，不能推断所有模型或改图接口。上游返回的 quality 和 token 数是其声明，不是独立测量出的视觉质量。单张耗时、文件大小、不同随机画面均不能证明质量档位生效。

## 可实现的方案

| 目标 | 实现方式 | 能保证什么 | 限制 |
| --- | --- | --- | --- |
| 横图、竖图、方图 | 继续在提示词写明画布比例，同时传 size | 本次提示词组能影响比例 | 不能承诺每次精确像素，应继续读取原图像素 |
| 指定像素导出 | 保存原图，另做导出副本；用成熟图像库等比缩放，提供裁切或留边 | 最终文件宽高可精确控制 | 放大不会凭空增加真实细节；裁切可能丢内容，留边可能不适合满版海报 |
| 文件体积档位 | 提供 JPEG/WebP 压缩参数，PNG 保留为无损原图 | 可以选择压缩程度 | 这是导出压缩质量，不是模型的 low/medium/high；文件大小仍取决于画面 |
| 更高清的细节 | 接入超分辨率服务，或经复测确认支持原生高清和质量档位的上游 | 可以提供单独的增强流程 | 超分可能改动小字、商标和产品纹理；需要新服务配置、成本及质量验证 |

推荐先做“原图保留 + 指定尺寸导出”，用户选择裁切/留边；把“高清增强”作为独立功能评估。不要把普通插值放大或 JPEG 压缩包装成模型 high 质量。

项目已有 `XI_XU_NORMALIZE_OUTPUT_SIZE=true`，只对可解码 PNG 做等比缩放、白底留边，并覆盖保存文件；不适合作为完整导出方案。此次没有开启该配置，也没有开放尚未验证有效的质量收费档位。

## 复测命令

以下命令会真实消耗上游额度：分别请求 6、3、1 张图片；不自动重试。只运行不带 `--run` 的命令不会调用上游。

```powershell
node scripts/probe-image-capabilities.js --run
node scripts/probe-image-capabilities.js --run --prompt-size
node scripts/probe-image-capabilities.js --run --prompt-quality
```

每次结果保存在 `output/image-probe-时间戳/report.json`，同目录保留原图、真实像素、文件大小和 SHA-256。请求逐个执行，每次最长等待 10 分钟；上游 HTTP 错误只记录状态码，避免错误正文泄漏认证信息。
